# Hive/Spark SQL 原工程代码梳理

仅梳理用户确认范围内的现有代码。保持只读，不执行任务或修改代码；不把代码中的预期处理当作实际运行结果。沿用当前会话中已经提供的目录、文件范围和答复，逐步补齐信息，避免重复询问。

## 第一步：识别入口并确认文件范围

1. 获取工程目录或代码位置。用户已经提供时直接使用；无法访问时说明原因，并请用户提供可访问的位置。
2. 查看目录结构，必要时读取文件片段，找出 SQL（如 `.sql`、`.hql`）、包含或调用 SQL 的 Shell/Python/Scala 文件，以及相关配置。此时只定位和初步分类。
3. 根据文件实际内容标记为 **DDL**（对象定义）、**查询/数据写入处理**、**DDL 与处理语句混合**、**调用/配置**或**待识别**。同一文件混合多类语句时，标明各类语句的大致位置；不要只凭扩展名或目录名判断，也不要要求拆分文件。
4. 向用户展示候选清单，包含相对路径、初步分类和简要用途。若文件很多，先按任务或目录分组，再展开用户选中的部分。**当用户只指定目录时，必须请用户确认本次针对哪些代码文件**，可确认全部、选择文件/子目录或排除部分。用户已明确指定文件时，复述范围并确认。
5. 记录已确认目录、文件和排除项，再进入第二步。后续发现必需的范围外依赖时，说明关联原因，请用户确认是否纳入后再深入阅读。

## 第二步：梳理执行顺序和数据链路

1. 在确认范围内，从任务入口阅读调用脚本、配置和 SQL，识别调用关系、执行顺序及参数来源。无法确认的顺序或运行时参数值标为未知。
2. 按语句识别输入、处理和输出。混合文件中的 DDL 与查询/写入语句分别分析，并说明定义的对象怎样被后续语句使用。关注来源表、中间表、临时视图、CTE、目标表、条件分支和动态 SQL。
3. 串联可核对的链路：**来源表 → 中间处理 → 目标表**。对关键环节标注文件与代码位置，说明关联、过滤、去重、聚合和写入；只纳入代码中能确认的直接调用与下游。
4. 随分析更新已确认链路和疑问。能说明主要入口、可确定的执行顺序和来源到输出的过程后，进入第三步；不要推测实际执行路径或结果。

## 第三步：按需补齐缺口

1. 记录尚不明确的入口、参数、表结构、字段含义、分区、业务口径和外部依赖，并指出它们影响哪段链路。区分**代码事实、基于代码的推断、未知事项**。
2. 先在确认范围内搜索 DDL、SQL、脚本和配置，核对同名对象与参数引用。需要读取范围外文件时，遵循第一步的范围确认规则。
3. 只有缺口阻碍继续梳理或会改变主要结论、且代码无法回答时，向用户询问当前最关键的 **1～2 个具体问题**。说明已有发现、所需信息及它影响的判断。不影响推进的疑问先记录，继续其他部分。
4. 根据用户补充的信息修正链路和结论，不重复询问已答复的问题。用户暂时无法补充时，记录原因及影响范围，完成其余可梳理部分。

## 第四步：汇总结果

按任务或目标表组织一份简洁的梳理结果，包含：

1. **工程概览**：确认的文件范围、入口、主要文件用途，以及 DDL、查询/写入、混合文件的分类。
2. **处理链路**：可确认的执行顺序、来源 → 中间处理 → 目标，以及关键文件和代码位置。
3. **核心逻辑**：数据粒度、字段来源、关联条件、过滤、去重、聚合口径、分区和写入方式；仅展开主链路所需细节。
4. **未确认事项**：无法确认的调用、参数、表结构或业务含义，以及对结论的影响。

为主要结论附文件及代码位置；用户补充的业务信息注明来源。代码与用户描述不一致时列明差异。确保结果能够回答“梳理了哪些代码、任务怎样组织、数据如何流动、核心 SQL 做什么、还有什么不能确认”。剩余缺口已说明影响范围时，可以交付当前结果。
