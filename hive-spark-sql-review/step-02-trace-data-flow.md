## 第二步：梳理代码执行顺序与数据处理链路

### 目标

在第一步确认的文件范围内，梳理代码如何被调用、SQL 按什么顺序执行，以及数据如何从来源表流向目标表。

### 执行流程

**1. 确定执行入口与顺序**

阅读调用脚本、配置和 SQL 文件，识别任务入口、文件间的调用关系、参数传递及执行顺序。若无法从现有代码确定实际运行顺序，记录这一缺口。

**2. 按语句梳理 SQL**

依照执行顺序，识别每段 SQL 的输入、主要处理和输出。对于 DDL 与 DML 混合的文件，按语句分别梳理，说明 DDL 定义了哪些对象，以及后续语句如何使用这些对象。

重点关注来源表、中间表或临时视图、CTE、目标表，以及动态拼接的 SQL。遇到动态参数时，记录参数来源；无法确定运行时取值的，明确标记为未知。

**3. 串联数据链路**

将相关语句整理为可核对的链路：

> 来源表 → 中间处理 → 目标表

对每个环节简要说明所用文件及代码位置、读取和写入的对象，以及关联、过滤、去重、聚合等主要处理。能从代码中确认的下游调用也纳入链路。

**4. 逐轮反馈发现**

梳理过程中持续记录已确认的链路和待查问题。只有缺失信息阻碍继续判断时，才向用户提出当前最关键的 1～2 个问题；其余疑问留待后续步骤集中说明。

### 完成条件

已能说明确认范围内的任务入口、可确定的执行顺序，以及主要数据从来源到输出的处理链路。无法从代码确认的环节应明确标注，不推测其实际运行结果。

若发现必需的依赖文件不在确认范围内，先说明它与当前链路的关系，请用户确认是否补充该文件，再继续深入梳理。
